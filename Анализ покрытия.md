# КТ №6 — анализ покрытия и результатов

Дата проверки: 12.11.2026. Сервер: https://petstore.swagger.io/v2.
Спецификация: https://petstore.swagger.io/v2/swagger.json.

## Что проверено

Основная часть: 20 позитивных и 19 выполняемых негативных сценариев.
Собираются 40 случаев pytest; негативный GET /user/logout явно пропущен,
поскольку в спецификации нет условий отказа. Все 40 имеют Allure feature,
story, severity. Полное выполнение пункта о негативе каждого запроса пока
не подтверждено: требуется конкретизация именно GET /user/logout.
Дополнительная часть: асинхронный клиент на aiohttp, замер покрытия pytest-cov и HTML-отчёт.

## Исправления после самопроверки

- PNG заменён на корректный 1×1 RGBA: проверены сигнатура, CRC всех блоков
  IHDR/IDAT/IEND и распаковка данных пикселя.
- Очистка во всех трёх фикстурах принимает только GET 200/404; GET 500
  вызывает ошибку. Для питомца проверяются ID и уникальный тег, для пользователя
  ID и имя, для заказа ID и petId. Чужие записи не удаляются.
- После DELETE проверяется GET 404, поэтому оставшаяся запись или ошибка
  сервера не выдаётся за успешную очистку.
- Эти условия проверены локально: 3 фикстуры × 7 случаев = 21 проверка:
  записи уже нет, GET 500, чужая запись, DELETE 500, проверочный GET 500,
  запись осталась после DELETE и успешное удаление. Все 21 прошли.
  Это отдельные проверки с подставными ответами, они не входят в 40 случаев Allure.
- PATCH /user/logout убран. Негативный GET пропускается до уточнения требований,
  сетевой запрос для него не выполняется.

## Разбор расхождений

- Сервер возвращает 500 при неверном числовом типе ID в JSON для семи операций: создание и изменение питомца, создание заказа, создание пользователя одиночно/списком/массивом и изменение пользователя. Примеры ответа: code 500, message "something bad happened". У операций user с default точный ожидаемый 400 является допущением.
- В четырёх операциях GET/DELETE по ID питомца и заказа вместо документированного 400 получен 404 с java.lang.NumberFormatException. Отдельно POST формы питомца возвращает 404 вместо указанного 405.
- uploadImage с нечисловым petId вернул 404; ожидаемый 400 в этом тесте принят нами: в Swagger у загрузки определён только успешный ответ.
- Поиск с invalid_status и поиск без обязательного tags возвращают 200 и пустой массив вместо отказа.
- Склад возвращает остатки с invalid-key; в Swagger есть security api_key, но конкретные ошибочные коды не описаны. Тест ожидает 401 или 403.
- Вход с неверным паролем возвращает 200 и "logged in user session" вместо документированного 400.
- Получение и удаление отсутствующего пользователя возвращают ожидаемый 404.
- У GET /user/logout нет определённого негативного поведения; PATCH больше не используется как его замена.

Пять из 17 падений связаны с принятыми ожиданиями, а не с явно заданными
ошибочными кодами: uploadImage (ожидаемый 400), inventory (401/403),
POST /user, createWithList и createWithArray (400).
Это гипотезы для проверки требований, а не пять доказанных контрактных дефектов.

## Соответствие презентации

1. Терминал Ubuntu доступен напрямую; WSL из слайдов 3–4 не нужен на Ubuntu.
2. pytest-cov установлен в локальную .venv, а не системный Python.
3. --cov=api_client задаёт именно исходный код клиента, аналогично --cov=src в примере.
4. --cov-report=term-missing даёт таблицу строк, --cov-report=html:htmlcov — HTML.
5. Разобраны фактические результаты и непокрытые возможности; процент не выдан за доказательство качества.

## Очистка и ограничения общего сервера

Питомцы и пользователи имеют случайные идентификаторы и префикс kt6_.
Заказ создаётся только на найденном свободном ID 1–10; после теста удаляется
только при совпадении ID и нашего petId. В текущем запуске заказы не пропускались.
Проверка принадлежности питомца использует ID и уникальный тег, а не просто
общий префикс kt6_. Ошибочные ответы очистки вызывают ошибку; после DELETE
выполняется GET 404. Повторный живой запуск не показал ошибок teardown.
Между проверкой ID заказа и записью возможна гонка на общем сервере.
Массовой очистки чужих записей, повторов до удобного статуса и зависимости
тестов от порядка нет. Подключение к учебному серверу разрешено пользователем.
