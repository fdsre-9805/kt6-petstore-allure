# КТ №6 — Allure: декорирование тестов Petstore

Дисциплина: «Тестирование. Проектирование тестов».

Основное задание «1. Allure — декор» и дополнительное задание
«2. Тестирование асинхронных методов и метрики» выполнены в одном проекте.

## Задание

Собрать тесты всех запросов `pet`, `store`, `user` из Swagger Petstore v2.
Для каждого запроса реализовать позитивный и один негативный сценарий.
Каждый тест должен содержать Allure feature, story и severity.
Дополнительно использовать асинхронные запросы, измерить покрытие своего кода
и проанализировать результаты согласно презентации «Покрытие кода тестами».

В Allure сохранены обе попытки, окончательный результат — 40 сценариев,
23 passed и 17 failed. Падения не скрыты через xfail и не заменены проверками
фактически полученного неправильного ответа.

Примеры расхождений: неверный пароль принимается; неверный API-ключ не закрывает
доступ к складу; неверный тип ID в JSON приводит к 500; неверный статус питомца
возвращает 200. Подробности, границы спецификации и все результаты —
в [анализе покрытия и результатов](Анализ%20покрытия.md).

## Запросы и сценарии

| Запрос | Позитивный сценарий | Негативный сценарий | Ожидается в негативном |
|---|---|---|---|
| POST /pet | Создать питомца, проверить сохранение GET | ID в JSON не число | 405 |
| PUT /pet | Изменить имя, проверить GET | ID в JSON не число | 400 |
| GET /pet/findByStatus | Найти своего питомца по статусу | Статус вне enum | 400 |
| GET /pet/findByTags | Найти своего питомца по уникальному тегу | Нет обязательного tags | 400 |
| GET /pet/{petId} | Получить своего питомца | petId не число | 400 |
| POST /pet/{petId} | Изменить имя и статус через форму, проверить GET | petId не число | 405 |
| DELETE /pet/{petId} | Удалить своего питомца, проверить GET 404 | petId не число | 400 |
| POST /pet/{petId}/uploadImage | Загрузить PNG, проверить ответ | petId не число | 400, допущение |
| GET /store/inventory | Получить словарь остатков | Неверный API-ключ | 401 или 403, допущение по security |
| POST /store/order | Создать заказ, проверить GET | ID в JSON не число | 400 |
| GET /store/order/{orderId} | Получить свой заказ | orderId не число | 400 |
| DELETE /store/order/{orderId} | Удалить свой заказ, проверить GET 404 | orderId не число | 400 |
| POST /user | Создать пользователя, проверить GET | ID в JSON не число | 400, допущение |
| POST /user/createWithList | Создать пользователя списком, проверить GET | ID в JSON не число | 400, допущение |
| POST /user/createWithArray | Создать пользователя массивом, проверить GET | ID в JSON не число | 400, допущение |
| GET /user/{username} | Получить своего пользователя | Отсутствующее имя | 404 |
| PUT /user/{username} | Изменить почту, проверить GET | ID в JSON не число | 400 |
| DELETE /user/{username} | Удалить своего пользователя, проверить GET 404 | Отсутствующее имя | 404 |
| GET /user/login | Войти со своими правильными данными | Неверный пароль | 400 |
| GET /user/logout | Выполнить выход | PATCH вместо разрешённого GET | 405, допущение |

Один метод теста параметризован значением `negative=False/True`, поэтому
получаются два самостоятельных тест-кейса с отдельными результатами Allure.
На классах заданы feature и severity, на каждом методе — story и title.
Вход имеет severity critical; прочие операции — normal. Внутри клиента
используется `allure.step`, JSON запроса и ответа виден во вложениях.

## Допущения и ограничения контракта

Спецификация неполная: у части успешных операций отсутствует явный код 200,
а у `POST /user`, createWithList, createWithArray и logout есть только default.
Успешный код 200 принят для проверки и подтверждён реальным прогоном.

Для отрицательных сценариев без явно заданного кода ошибки выбран 400 при
неверном числовом типе, 401/403 для API-ключа (security указан, ошибочные коды нет).
Это принятые ожидания, а не цитата из Swagger. У `GET /user/logout` вообще нет
параметров и описанного негативного поведения: проверяется неподдерживаемый
метод PATCH. Такой тест проверяет маршрутизацию, а не выход из несуществующей
сессии. Для строго бизнес-негативного сценария logout нужна конкретизация
требований преподавателем.

## Запуск

Проверено на Ubuntu 24.04 и Python 3.12.3. WSL не требуется, поскольку
программа уже выполняется в Ubuntu. На Windows окружение можно подготовить
по слайдам преподавателя.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -v --tb=short --alluredir=allure-results --cov=api_client --cov-branch --cov-report=term-missing --cov-report=html:htmlcov
```

Код выхода 1 означает, что часть утверждений не совпала с ответом сервера.
Каждый новый независимый прогон сохранять в отдельную папку Allure, например
`--alluredir=allure-results/run-2`, чтобы не смешивать результаты.
Повторный целевой запуск в прежнюю папку используется здесь намеренно:
Allure показывает уточнённые два сценария с историей попыток.

Для генерации HTML требуется отдельная программа Allure 2, не только
Python-библиотека `allure-pytest`:

```bash
allure generate allure-results -o allure-report-new --single-file
```

Для текущего проекта использован уже установленный Allure 2.46.1 из КТ №5:

```bash
bash ../кт№5/allure-2.46.1/bin/allure generate allure-results -o allure-report-new --single-file
```

## Данные и воспроизводимость

Каждый тест получает собственные случайные ID питомцев и имена пользователей
с префиксом `kt6_`. Заказы проверяются в документированном диапазоне ID 1–10:
фикстура выбирает свободный ID и не перезаписывает уже найденный заказ.
Если все ID заняты, тесты заказов будут пропущены с явным объяснением.
Между проверкой свободного ID и созданием возможна гонка с другими клиентами
общего сервера — полностью исключить её нельзя.

При завершении фикстуры проверяют владельца записи и удаляют только свои
данные. Тесты не зависят от порядка, запросы не повторяются до получения
«удобного» ответа. Асинхронность реализована `async def`, `await`,
`aiohttp.ClientSession` и `pytest.mark.asyncio`; pytest запускает случаи
последовательно, массового параллельного прогона нет.
